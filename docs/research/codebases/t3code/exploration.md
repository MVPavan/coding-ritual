# T3 Code — control-plane exploration

> Repository: https://github.com/pingdotgg/t3code · pinned commit `9383f4ad71285b9f9a6a9b65f2f961ea2cf4308f` (shallow clone) · 2026-09-24. No live probe; nothing was run. Citations use pinned `t3code:path:line`. `[read]` means observed in source or docs; `[inferred]` means a bounded conclusion from what was read.

Question: can T3 Code replace our foreman, inspector, and crew profiles as the control plane for keyed, headless, one-process-per-turn activations, or does it offer patterns worth borrowing?

## T0 — What it is and how it runs

- [read] T3 Code is an MIT-licensed "agent harness control surface": a Node WebSocket server wraps provider CLIs (Codex, Claude Code, Cursor, Grok, OpenCode, Antigravity) and serves web, desktop (Electron), and mobile clients. `t3code:LICENSE:1` `t3code:AGENTS.md:3` `t3code:README.md:3`
- [read] The server runs without Electron via `t3` / `npx t3` (commands `start`/`serve`); Electron is only the desktop shell that bundles the server. Node `^22.16 || ^23.11 || >=24.10` is required. `t3code:README.md:37` `t3code:apps/server/src/cli/server.ts:21` `t3code:apps/server/package.json:52` `t3code:AGENTS.md:39`
- [read] No T3 account is needed for a local server; each vendor CLI must be installed and logged in (`codex login`, `claude auth login`, ...). Clients authenticate to the server with pairing/session tokens. `t3code:README.md:13` `t3code:apps/server/src/cli/auth.ts:84` `t3code:docs/internals/overview.md:16`
- [read] Architecture: typed WS request → command → pure decider → persisted events → projector read model. Provider CLIs are subprocesses; per-provider adapters normalize their native protocols into canonical runtime events; queue-backed reactors perform side effects. Each turn ends with a hidden git-ref checkpoint. `t3code:AGENTS.md:138`

## H1 — Headless launch and result capture

- [read] Claude is driven through `@anthropic-ai/claude-agent-sdk` `query()`, not `claude -p`. Options set `cwd`, `model`, `effort`, `permissionMode`, `resume` or a pre-minted `sessionId`, `settingSources`, `pathToClaudeCodeExecutable`, env, `additionalDirectories`, and passthrough `extraArgs`. The prompt is an async iterable fed from an in-memory queue, so one Claude process serves many turns. `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:5` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:4421` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:4428` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:4913`
- [read] Codex is driven through a long-lived `codex app-server` child (JSON-RPC over stdio) via the repo's own `effect-codex-app-server` package; `CODEX_HOME` and extra launch args are configurable. Model, effort, sandbox policy, and approval policy are sent per `turn/start`. `codex exec` is used only for side text generation (titles etc.). `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:1316` `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:1327` `t3code:apps/server/src/provider/Layers/codexLaunchArgs.ts:12` `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:641` `t3code:apps/server/src/textGeneration/CodexTextGeneration.ts:199`
- [read] The adapter contract is session-oriented: `startSession`, `sendTurn`, `interruptTurn`, `stopSession`, `readThread`, `rollbackThread`, and one canonical `streamEvents`. Nothing in it is one-process-per-turn. `t3code:apps/server/src/provider/Services/ProviderAdapter.ts:67`
- [read] The structured result is the canonical `turn.completed` event: `state` ∈ `completed | failed | interrupted | cancelled`, plus `stopReason`, usage, cost, and `errorMessage`. The final assistant text and diff are not in that payload; they arrive as separate item events and checkpoint diffs. `t3code:packages/contracts/src/providerRuntime.ts:74` `t3code:packages/contracts/src/providerRuntime.ts:348`
- [read] Claude outcome grading lives in `resultOutcome`: success-tagged `is_error`, 529 overload reported as `success`, and `terminal_reason` aborts are mapped explicitly. `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:1681` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:1690` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:595`
- [read] The process exit code is a session fact, not a turn fact. Codex app-server exit becomes `session/exited` with the code. On Claude stream end or failure, an in-flight turn is completed as `interrupted`/`failed`, and no CLI exit status is surfaced in the inspected path. `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:2405` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:4229`

## H2 — Turn-boundary reliability

- [read] Claude: a turn ends on the SDK `result` message (`handleResultMessage` → `completeTurn`) or on stream exit. A result with no local turn state (resume handshake, late result after a steer auto-close) is logged and does not emit a lifecycle event. `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:3483` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:2740`
- [read] Steering is not a turn boundary: `sendTurn` during a running real turn queues the message into the live SDK loop and continues the same `turnId`. Stale synthetic turns are auto-closed as `completed` before the next user turn. `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:5153` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:5160`
- [read] Codex: boundaries come from app-server `turn/started` and `turn/completed` notifications. `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:790`
- [inferred] Boundaries are protocol-derived, which is better than screen state. Because a session spans turns, "turn ended" and "process ended" are separate facts. Steering folds into the running turn, while ours creates a new continuation turn.

## H3 — Event stream durability and ordering

- [read] Orchestration events are appended to SQLite with per-stream `stream_version` and a global `sequence`. Events, projections, and the command receipt commit in one transaction; subscribers see events only after commit. SQLite runs in WAL mode with `busy_timeout=5000`; `synchronous` is not set in the inspected setup. `t3code:apps/server/src/persistence/Layers/OrchestrationEventStore.ts:129` `t3code:apps/server/src/orchestration/Layers/OrchestrationEngine.ts:274` `t3code:docs/internals/overview.md:55` `t3code:apps/server/src/persistence/Layers/Sqlite.ts:15`
- [read] Provider runtime events first pass through in-memory unbounded queues in the adapters, then are ingested as orchestration commands. Ingestion command IDs embed a fresh random UUID (`provider:<eventId>:<tag>:<uuid>`), so replaying the same provider event would not deduplicate by receipt. `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:1301` `t3code:apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts:1032`
- [read] Raw native/canonical provider events can also be written to rotating NDJSON logs, documented as best-effort. `t3code:apps/server/src/provider/Layers/EventNdjsonLogger.ts:3`
- [inferred] Provider events that are in flight in memory when the server crashes are lost. The durable log records only what was ingested.

## H4 — Resume and recovery after crash or restart

- [read] A per-thread provider session binding (`resumeCursor`, `runtimePayload`, status) is persisted. The Claude cursor holds the session UUID, `resumeSessionAt` (last assistant UUID), and turn start message IDs; the Codex cursor holds the thread ID. `t3code:apps/server/src/persistence/ProviderSessionRuntime.ts:36` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:2192`
- [read] Claude session IDs are minted by T3 before launch (`randomUUIDv4` → `sessionId`) unless resuming, which matches our pattern. Codex IDs come from `thread/start` / `thread/started`. `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:4421` `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:741`
- [read] Codex `thread/resume` falls back silently to a fresh `thread/start` (with only a warning log) when the error text matches "not found", "no rollout found", and similar strings. `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:59` `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:765`
- [read] On startup, threads whose projection says `starting`/`running` but have no live provider session are settled as `error` ("did not survive a server restart"). If the user enabled `continueThreadsAfterServerUpdate`, the server instead resumes and sends "Continue where you left off." (or a promptless continuation). A durable marker guards against a crash between preparing and sending. `t3code:apps/server/src/serverRuntimeStartup.ts:345` `t3code:apps/server/src/serverRuntimeStartup.ts:536` `t3code:apps/server/src/serverRuntimeStartup.ts:583` `t3code:apps/server/src/serverRuntimeStartup.ts:662`
- [read] Idle provider sessions are reaped after an inactivity threshold. `t3code:apps/server/src/provider/Layers/ProviderSessionReaper.ts:31`
- [inferred] Recovery does not reconstruct what the interrupted turn did. It either marks the turn failed or nudges the agent to continue, so no keyed settlement of the in-flight turn exists.

## H5 — Fit as a substrate under our inspector

- [read] Command idempotency is real but scoped to T3 commands: a `commandId` receipt returns the prior result, rejects reuse against another aggregate, and replays prior rejections. `t3code:apps/server/src/orchestration/Layers/OrchestrationEngine.ts:144`
- [read] Per-turn git checkpoints: hidden refs `refs/t3/checkpoints/<b64 thread>/turn/<n>`, built with a temporary index plus `add -A`, `write-tree`, `commit-tree`, and `update-ref`, so the user's branch and index stay untouched. A baseline is captured on turn-start-requested/turn.started, and a post-turn checkpoint on `turn.completed`/`turn.aborted`. `t3code:apps/server/src/checkpointing/Utils.ts:4` `t3code:apps/server/src/vcs/GitVcsDriver.ts:1007` `t3code:apps/server/src/orchestration/Layers/CheckpointReactor.ts:393` `t3code:apps/server/src/orchestration/Layers/CheckpointReactor.ts:656`
- [read] The baseline is best-effort: a missing pre-turn baseline is logged as a warning and capture proceeds. `t3code:apps/server/src/orchestration/Layers/CheckpointReactor.ts:277`
- [inferred] The baseline is captured by a reactor after the turn-start intent commits, separately from the provider command reactor that launches the turn. I found no ordering guarantee that the baseline exists before the agent writes, so it is not a proven input pin.
- [read] External control: there is no CLI command to create a thread or run a turn (CLI commands are service, project, auth, pair, update, and similar). The programmatic surface is the authenticated WebSocket RPC `dispatchCommand` with `thread.turn.start` plus subscriptions. `t3code:apps/server/src/cli/project.ts:571` `t3code:packages/contracts/src/rpc.ts:1275` `t3code:packages/contracts/src/orchestration.ts:1306`
- [inferred] Using T3 as a substrate would mean running a Node server, pairing a token, and driving threads over WS RPC. We would inherit long-lived sessions, T3's thread/turn model as a second ledger, and its own checkpoint refs. It is a product server for humans, not a library.

## Verdict

[inferred] **REJECT as control plane; BORROW-SELECTIVELY (small, mostly reference).** T3 Code is a well-engineered, MIT, Node server product whose unit is a long-lived provider session per human thread. That contradicts our one-headless-process-per-turn, keyed-activation model. Adopting it would add a second ledger, a WS/auth server dependency, and steering semantics opposite to ours. Its turn facts are protocol-derived (SDK `result`, app-server `turn/completed`), which is sound but not better than what our profiles already parse. `t3code:apps/server/src/provider/Services/ProviderAdapter.ts:67` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:5153`

Borrow candidates, smallest first:

1. **Claude result edge-case table** — compare our Claude profile's grading against T3's `resultOutcome`/`isInterruptedResult`: a `success` subtype with `api_error_status: 529` is a failure; success with `is_error: true`; `terminal_reason` `aborted_tools`/`aborted_streaming` means interrupted. These are the same stream-json `result` fields we parse. Convert them to contract tests only if a live `claude -p` run shows the same fields (not verified here). **Effort: low.** `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:1681` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:1690` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:595`
2. **Counter-pattern for Codex resume: never silently fall back to a fresh thread.** T3 turns "thread not found" into a new thread with a warning. For us a failed resume must surface as a failed/doubt activation, because a fresh thread breaks continuation semantics. Check that our `codex exec resume` path fails loud. **Effort: low (audit).** `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:59` `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:765`
3. **Hidden-ref checkpoint without touching the user index** (temp `GIT_INDEX_FILE` + `add -A` + `write-tree` + `commit-tree` + `update-ref` under a private namespace), including its nested-repo/sparse-checkout edge handling. This is reference only: our inspector already pins trees. Consult it if our pinning hits embedded repos or sparse checkouts. **Effort: low to read, medium to adapt.** `t3code:apps/server/src/vcs/GitVcsDriver.ts:794` `t3code:apps/server/src/vcs/GitVcsDriver.ts:1042`
4. **Command receipt that rejects a reused ID aimed at a different aggregate** (`OrchestrationCommandIdConflictError`) and replays prior rejections. This is the same shape as Orca's `request_mismatch` (comparison doc item 2); relevant only if we add an external caller-supplied request ID. **Effort: medium if that API appears; otherwise defer.** `t3code:apps/server/src/orchestration/Layers/OrchestrationEngine.ts:144`

Do not borrow: the restart "Continue where you left off." nudge (it hides the lost turn instead of settling it), random-UUID ingestion command IDs, or best-effort baselines. `t3code:apps/server/src/serverRuntimeStartup.ts:348` `t3code:apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts:1032`

## Limits

- [read] One static pass; no server was run, no provider was driven, no crash was induced. Claude- and Codex-specific claims come from adapter code, not observed vendor output.
- [inferred] I did not verify that the Agent SDK `result` message fields (`terminal_reason`, `api_error_status`) appear identically in `claude -p --output-format stream-json`. Borrow item 1 is conditional on that check.
- [inferred] I did not read the `ProviderCommandReactor`/`CheckpointReactor` scheduling in full, so the claim that the baseline is not ordered before provider launch is unproven either way. Cursor, Grok, OpenCode, and Antigravity adapters were not read.
