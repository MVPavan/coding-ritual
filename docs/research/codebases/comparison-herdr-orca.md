## Question and boundary

Can Herdr, Orca, Traycer, or T3 Code replace the workflow interpreter's agent control plane—inspector, crew profiles, and foreman dispatch—while everything else stays unchanged?

The foreman mints a keyed graph-node activation and owns the deterministic SQLite ledger. The inspector runs one headless vendor CLI process per turn (`claude -p --output-format stream-json` or `codex exec --json`), with pinned model/effort, isolation flags, and a worktree. Claude's profile mints a UUID before launch and passes `--session-id`; Codex instead captures `thread.started` from its stream. Both resume the vendor session on a later activation. The inspector proves and pins input/output git trees, grades the structured exit log into success/fail/doubt plus final message and diff, and routes on that result. Steering is a new continuation turn, not terminal typing; delivery and recovery are keyed and crash-safe. `workflow_interpreter/profiles/claude.py:198` `workflow_interpreter/profiles/codex.py:197` `workflow_interpreter/inspector/launch_record.py:24`

## Who produces turn facts today, and would launching through herdr help?

- [read] The OS supplies the vendor CLI's exit status when its process exits; the inspector reaps, records, and grades it. The process lifetime is one headless turn. `workflow_interpreter/inspector/monitor.py:164` `workflow_interpreter/inspector/exit.py:197` `workflow_interpreter/profiles/claude.py:210`
- [read] Turn content comes from the CLI's structured stream, captured in the exit log and parsed by our profiles: Claude's `stream-json` `result` frame; Codex `exec --json` events, including `turn.completed` and agent messages. Claude's session UUID is minted here and passed via `--session-id`; Codex's thread ID is read from `thread.started`. `workflow_interpreter/profiles/claude.py:198` `workflow_interpreter/profiles/claude.py:302` `workflow_interpreter/profiles/codex.py:213` `workflow_interpreter/profiles/codex.py:352` `workflow_interpreter/inspector/profile.py:366`
- [read] Input/output git-tree proof, launch receipt, crash recovery, and idempotent activation keys are our inspector/ledger work; neither terminal tool supplies them. `workflow_interpreter/inspector/workspace.py:330` `workflow_interpreter/inspector/workspace.py:406` `workflow_interpreter/inspector/launch.py:301` `workflow_interpreter/inspector/recover.py:1` `workflow_interpreter/ledger/schema.py:82`
- [inferred] Launching the same headless vendor CLIs through Herdr would return PTY terminal text, which can contain ANSI and be truncated, without a caller-visible exit code. Herdr's screen manifests would not apply to our headless output, and Herdr would pass the same argv to the same vendor CLI; vendor-flag drift remains. This adds a runtime dependency without removing the fragile CLI contract. `herdr:src/pane.rs:2271` `herdr:src/api/schema/panes.rs:757` `herdr:src/api/schema/events.rs:526` `herdr:src/detect/manifest.rs:431`
- [inferred] T3 Code gets turn facts from vendor protocols over long-lived sessions (Agent SDK `result`, app-server `turn/completed`), not from process exit. Routing our turns through it would swap the per-turn exit status we reap today for a session-level exit, and would add a Node server plus WS auth between the foreman and the CLI. `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:2405` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:4229`
- [inferred] Useful stability levers are pinning vendor CLI versions and running small per-vendor contract tests. A separate spike could evaluate the Claude Agent SDK, Anthropic's supported programmatic interface, as the Claude crew transport; that is an option, not a verified migration. `workflow_interpreter/profiles/claude.py:4` `workflow_interpreter/profiles/codex.py:7`

## Worth borrowing, ranked

Effort is an engineering estimate for adapting a mechanism inside our existing inspector/ledger, not for installing Herdr, Orca, or T3 Code. Items 1–3 are conditional studies, not identified gaps in current activation safety. Traycer adds no borrow candidate.

1. **Explicit provider-submission states: `pending/accepted/rejected/unknown`, without automatic resend.** Orca reconciles uncertain sends from provider history. Our pre-exec `LaunchReceipt` already identifies a launch, including the `REATTACHED` window, and §5.6 recovery classifies liveness without a crash loop. The possible delta is finer provider-acknowledgement evidence *within* a launched CLI turn; defer until a real unresolved continuation case shows our exit-log recovery insufficient. **Effort: medium.** `orca:src/shared/agent-session-journal-types.ts:337` `orca:src/main/native-chat/agent-session-journal/journal-pending-submission-recovery.ts:4` `workflow_interpreter/inspector/launch_record.py:24` `workflow_interpreter/inspector/recover.py:1` [read]/[inferred]
2. **Mutation payload receipts keyed by `(callerFingerprint, requestId)`.** Orca returns `request_mismatch` for a changed request and `operation_unknown` for accepted replay. Our deterministic natural keys already make a re-tick find an existing activation, and mint facts derive from the pinned graph/trace. The narrow delta would be rejecting changed payloads under an *external caller-supplied request ID* if such a control API is added; do not duplicate our current mint identity. **Effort: medium if that API appears; otherwise defer.** `orca:src/main/runtime/orchestration/db/worker-dispatch/worker-dispatch-start.ts:48` `workflow_interpreter/bdio/keys.py:1` `workflow_interpreter/bdio/mint.py:116` [read]/[inferred]
3. **Per-session SQLite journal with WAL and `synchronous=FULL`.** Orca stores provider messages and turn state in a durable session journal. Our activation ledger and exit log already preserve turn evidence; the possible delta is a resumable, queryable cross-activation provider history only if a concrete recovery/query need emerges. Avoid a competing task authority. **Effort: medium to high; defer.** `orca:src/main/native-chat/agent-session-journal/journal-database.ts:23` `workflow_interpreter/inspector/recover.py:21` [read]/[inferred]
4. **Claude result edge cases as contract tests (conditional).** T3 grades `success` + `api_error_status: 529` as failed, `success` + `is_error: true` as failed, and `terminal_reason` `aborted_tools`/`aborted_streaming` as interrupted. Check that our Claude profile handles the same `result` fields, after a live `claude -p --output-format stream-json` run confirms they appear there. **Effort: low.** `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:1681` `t3code:apps/server/src/provider/Layers/ClaudeAdapter.ts:595` [read]/[inferred]
5. **Codex resume must fail loud (counter-pattern).** T3 falls back from `thread/resume` to a fresh `thread/start` on "not found"-style errors. Audit that our `codex exec resume` failure grades as fail/doubt and never becomes a fresh session. **Effort: low.** `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:59` `t3code:apps/server/src/provider/Layers/CodexSessionRuntime.ts:765` [read]/[inferred]
6. **Exact-process-incarnation mailbox pointer delivery.** Orca reserves a pointer for a specific PTY/process, settles accepted writes, and leaves unverifiable Enter ambiguous. For us: adapt the fencing and ambiguity states only if future inter-agent messaging needs a mailbox; our current continuation path does not type into PTYs. **Effort: high.** `orca:src/main/runtime/orchestration/mailbox-pointer-submit.ts:59` `orca:src/main/runtime/orchestration/mailbox-pointer-submit.ts:138` [read]/[inferred]
7. **Per-agent screen manifests as optional human visibility.** Herdr's Claude/Codex manifests show activity/blockers in an attached terminal, but unmatched Codex can stay unknown. For us: first try a pane tailing existing logs/transcripts for human visibility; a native attached terminal needs PTY ownership and must never route or grade work. **Effort: low for log tail, high for PTY integration; defer.** `herdr:src/detect/manifests/claude.toml:7` `herdr:src/detect/manifests/codex.toml:6` `herdr:src/pane.rs:2271` [read]/[inferred]

Reference only: T3's hidden-ref checkpoint with a temp `GIT_INDEX_FILE` and nested-repo/sparse handling, if our tree pinning hits those cases; and its `OrchestrationCommandIdConflictError` receipt check, which folds into item 2. `t3code:apps/server/src/vcs/GitVcsDriver.ts:794` `t3code:apps/server/src/orchestration/Layers/OrchestrationEngine.ts:144` [read]/[inferred]
