# Workstream: DWS — Deep Web Search

## Vision

**One deep web search tool that every project can use.**

Today each project rebuilds the same mechanical half of research — search
clients, scrapers, retries, PDF handling, storage, retrieval — and each copy
rots separately. DWS supplies that half once, as a local service, so projects
keep only their own research methods.

The cut is deliberate. Research methodology and models change fastest, so they
stay outside the product entirely, in host agents and skills. Retained evidence
is the stable foundation: while a snapshot is retained its content never
changes, and it carries hashes, a line map and provenance so it stays
verifiable after the live page has moved on. Retention itself is a policy
decision — pinned evidence survives normal cleanup, unpinned evidence may
expire explicitly rather than silently. DWS is the narrow seam between the two
halves: seven capabilities, provider-neutral, model-free by default.

Success is the negative result: throw away the research agent, switch models,
or start an unrelated project, and the acquisition, storage and retrieval layer
does not move — and a pinned citation from the old project still resolves to
the capture it named.

## Scope

**Delivery A — engine and CLI (phases P1–P11).** The complete Python application
core, local command daemon, independent worker, provider adapters, canonical
evidence storage, QMD lexical indexing, retention and restore tooling, driven by
a real `dws` CLI. FastMCP is not installed.

**Delivery B — MCP wrapper (phase P12).** A thin FastMCP adapter over the same
application facade. Its file-level plan is written against the completed engine.

Out of scope throughout: internal research planning or synthesis, model
inference, vectors, default OCR, mandatory Firecrawl/TinyFish/Spider, remote
exposure, authenticated scraping, and any second database engine.

The implementation plan retains its original v1.0 planning context; current
requirements and technical contracts come from the v1.1 baselines above.
Beads `spec_id` identifies what is built; `design` identifies the phase roadmap,
not the technical design companion.

Implementation authorization comes from the active owner goal described in
`docs/plans/dws/implementation-goal.md`, not from the presence of this roadmap
or the goal document. That goal covers Delivery A (P1–P11); Delivery B (P12)
remains a subsequent goal. Neither document presence nor authorization implies
implementation completion; Beads and recorded verification carry actual progress.

## Tracking

- One Beads epic per roadmap phase, titled `[P<n>] <phase name>`, labelled
  `ws-dws`, with `--spec-id docs/brainstorms/dws/DWS_PRD.md`
  and `--design docs/workstreams/dws/roadmap.md`.
- Flat stage children (no sub-tasks) carry the roadmap row's `Verify` cell as
  acceptance. Flat does not mean unordered: stage→stage edges declared in the
  roadmap are seeded as real dependencies.
- Per-phase plans land in `plans/` just in time, against the code that phase
  will actually encounter.
- `tracking/` is generated by the render script and never hand-authored.
- Beads owns execution status. This roadmap carries no checkboxes.

## Standing constraints

All fifteen invariants from the technical design (INV-01…15) govern every phase;
they are listed in the roadmap header and are not restated per stage.
