# P3 Implementation Plan — Independent Workflow Recovery

**Origin:** approved coordination spec, roadmap P3, and the owner's 2026-09-11 simplification.
**Goal:** let the orchestrator start, observe, collect, cancel, and recover independent pinned workflows under one finite owner allowance.
**Stage:** `cr-148.1`.
**Status:** approved after scoped independent correction review; P2 exit passed. Ready for implementation. This plan makes no Beads changes, implementation changes, commits, delegation, or live calls.

## Boundaries

P3 coordinates independent workflows only. The orchestrator chooses subsequent work after inspecting collected results. It does not create a child dependency DAG, wait for dependencies, bind one child's output into another child's inputs, select a graph automatically, integrate sibling work, land a target, or close a bridge stage.

Keep Foreman deterministic and each workflow single-head. Reuse Supervisor/profile execution, canonical graph/config pins, process evidence, worktrees, and the existing Beads-backed owner metadata. Do not add a database, scheduler daemon, runner, or model-decision lifecycle. P2's whole-member reservations remain monotone: each child reserves its complete finite local activation ceiling against the original owner's pinned `CoordinationLimits`; no refund or per-tick owner debit is introduced. Human gates and their authority remain unchanged.

## Existing P2 foundation

`WorkflowStore.coordination_store()` exposes `CoordinationStore`. Its owner-root `CoordinationState` already persists reservations, current slots, decision requests, and `human_attention`; `MemberAdmission` contains pinned graph/config/inputs/base data; and `admit_member(owner_id, slot, generation, admission, kind=...)` durably reserves, keyed-creates, and binds a root as a `MemberReceipt`. `validate_member` fences stale generations, while `coordination_view` reports the owner ledger. P3 extends these records rather than duplicating persistence.

The initial P3 child admission is generation `0`, uses `kind="child"`, and has a unique caller-chosen slot. A supplied admission must already pass the normal loader/config resolution and have a positive finite ceiling. Replaying the same immutable admission returns its existing receipt; conflicting slot/generation or admission replay refuses. A root with an incomplete reservation/linkage never dispatches.

## Interfaces

Add the following narrow coordination operations on `CoordinationStore` (then expose matching `children` subcommands from the existing `workflow_interpreter.foreman` module entry point):

| Operation | Durable result and rule |
|---|---|
| `start_child(owner_id, slot, admission) -> MemberReceipt` | Validate a standalone `MemberAdmission`; call the existing `admit_member(owner_id, slot, 0, admission, kind="child")`; record child lifecycle state. It admits no successor and injects no input. Reject supplied predecessor/request lineage. Until P5 supplies child replacement lifecycle integration, refuse child policies permitting replacement explicitly at admission; continue/human decisions remain supported. |
| `child_status(owner_id) -> ChildCoordinationView` | Return the owner reservation totals plus one row per admitted child: slot, generation, root ID, lifecycle state, latest activation/process references, and any cancellation/collection receipt. It is a read; it does not drive work. |
| `collect_child(owner_id, slot, generation) -> CollectedChildResult` | Accept only the current, non-cancelled member after existing terminal/evidence reads prove a settled result. Persist immutable root, generation, base, artifact/tree, terminal, and evidence references. A collection is idempotent; it is neither dependency satisfaction nor landing authority. |
| `cancel_child(owner_id, slot, generation, request_key, reason) -> CancellationReceipt` | First persist an idempotent cancellation intent and fence dispatch/result collection. Then use existing Supervisor handle/recovery and termination proof. Mark `cancelled` only after death is proved; missing or indeterminate process evidence stays `cancel_pending` and blocks restart/collection. Late output is retained as evidence but cannot become a collected result. |
| `recover_child(owner_id, slot, generation) -> ChildCoordinationView` | Reload the same receipt, launch/process evidence, and cancellation intent; repair only durable in-progress work. It never creates a root, reservation, generation, or replacement. A live child remains running; a proved stopped, uncancelled recoverable child may resume its existing local Foreman lifecycle. |
| `drive_children(owner_id, max_concurrent, max_wall_s) -> ChildCoordinationView` | Run ordinary per-root Foreman work for eligible children, at most `max_concurrent` at a time. Require `1 <= max_concurrent <=` a finite owner-admitted child count; do not queue unbounded work or hold the owner lock while a process runs. |

Command spelling is deliberately small: `children start`, `children status`, `children collect`, `children cancel`, `children recover`, and `children drive`. P3 defines their required owner/slot/generation and idempotency arguments; P5 owns the final normal-entry documentation and parser/config acceptance matrix.

## Execution rules

Before dispatch, P3 calls `validate_member` under the existing member exclusion and rechecks it immediately before launch. It retains P2's owner-lock-before-member-band order for short metadata transitions; process signalling, waiting, and ordinary execution occur outside the owner lock. A cancelled or stale member cannot mint, steer, dispatch, or collect.

Writer isolation is mandatory: a child whose pinned graph contains a writing node must execute in its own worktree. Two writer children therefore need distinct worktree and Git identities before either is launched. P3 does not permit shared target checkout mutation, sibling merge, or concurrent landing. Non-writing children retain their normal pinned isolation policy.

`max_concurrent` is an explicit finite operator/session bound, not an entitlement to start all admitted children. A driver timeout reports existing identities and leaves them recoverable; it does not imply cancellation or replenish capacity. Any uncertain lock, root linkage, process identity, or termination outcome fails closed to the persisted human-attention reason.

## Acceptance tests

Write focused deterministic tests before implementation, using the public Foreman module entry point and persisted Beads/Git state where the interface crosses it.

1. Start two distinct finite, pinned child admissions under one owner; prove each has one `MemberReceipt`, a `kind="child"` reservation, and no duplicate root after identical replay. Refuse conflicting replay and owner capacity exhaustion.
2. Use ordinary deterministic writer profiles and worktrees to prove two writer children have distinct worktree/Git identities and overlap while `max_concurrent=2`. With `max_concurrent=1`, prove only one is active. No test may manufacture a completion or collection record.
3. Restart the driver during running work, then `recover_child`; prove the same root, reservation, process evidence, and local lifecycle continue with no new admission or generation.
4. Cancel a running child across intent, signal, and recovery boundaries. Prove collection/dispatch are fenced before termination, `cancelled` requires termination proof, indeterminate death remains pending, and late output cannot collect.
5. Collect a settled current child exactly once; prove the receipt retains immutable evidence/artifact references, contains no downstream input binding, and does not change bridge/landing/stage closure state.
6. Exercise `children start/status/collect/cancel/recover/drive` through the actual parser with malformed owner/slot/generation, stale generation, and non-finite/out-of-range concurrency refusals.

Run the focused P3 suite plus affected Supervisor/Foreman recovery and worktree tests. Before phase exit, run the repository workflow-interpreter gate from `.codex/project/verification.md`, record actual exits, and inspect `git status`; P3 is not complete merely because planning exists.

## P4/P5 handoff

P3 supplies immutable collected-child references and lifecycle evidence only. P4 must explicitly select its source set, create a fresh serialized integration attempt against the current target, and obtain review, verification, and approval for the resulting combined artifact; a child collection or prior child approval is never authorization to land.

P4 owns bridge current-generation binding and required-contribution guards on direct/recovery landing and closure, preserving distinct successor execution and target CAS bases. P5 owns final normal-entry wiring and the explicit trusted graph/model replacement operation with lineage, quiescence, capacity and stale-predecessor guards. P3 neither implements nor authorizes these operations. The updated roadmap records this transfer.

## Risks and non-goals

Cancellation proof and canonical worktree identity are the safety-critical seams; characterize both before changing them. A terminal-looking child without authoritative current-generation evidence is not collectible. No live-runtime proof, integration, bridge replacement, automatic orchestration, or child-to-child dataflow belongs to this phase.

## Implementation ownership and corrected safety seams

All tasks serve `cr-148.1` and are test-first at public CLI/process boundaries. One implementer owns the following files; preserve prior P1/P2 edits. Execute tasks in order, using existing P2 APIs rather than duplicating their ledger.

| Task | Files and responsibility | Proof |
|---|---|---|
| 1: durable start and identity | `schema/decisions.py`, `bdio/wire.py`, `bdio/coordination.py`; child records, keyed admission and canonical identity | identical replay, conflicting lineage, capacity, different-wrapper-home duplicate drivers |
| 2: drive, cancellation and recovery | `bdio/api.py`, `foreman/supervise.py`, `foreman/decisions.py`, `foreman/children.py`, narrow Supervisor path/band/recovery seams as required | two ordinary isolated writers truly overlap; restart; launch-publication cancellation races; late evidence remains recordable |
| 3: collection and normal CLI | `foreman/children.py`, `foreman/__main__.py`, `tests/test_children_lifecycle.py`, `tests/test_children_cli.py`, `tests/test_children_process.py`; bounded reports and verified results | actual parser, immutable output evidence, failed/escalated children, no landing or stage closure |

Canonical exclusion derives from the real Beads workspace and owner/root identity, never the caller's wrapper home. Persist one authoritative wrapper location per admitted member and use it on recovery; competing configurations must reuse it or refuse before launch. Test distinct compositions with different wrapper homes. Use independent lock handles across threads/processes; object-local reentrancy is not a thread mutex. Maintain short owner-before-child lock order; never hold owner exclusion through execution, signalling or waiting.

Persist child lifecycle records keyed by slot/generation, selected activation/cancellation intent, and child-scoped failure or attention. Model transitions explicitly: admitted/running/settled/collected and cancel_pending/cancelled. Cancellation fences mint, steer, launch and collection before signalling; exit/evidence/termination recording remains allowed. Reconcile the launch-publication race using existing handles and wrapper recovery. Missing or indeterminate process proof is not death. Child cancellation must not set owner-global attention that stops siblings.

For a successful collection identify the current final activation and completed lifecycle, immutable output ref/tree and repository artifact evidence. Recompute the output ref's tree and compare with recorded evidence; persist graph/config/base identity and receipt digest. Never substitute mutable branch HEAD. Perform collection's final current-generation/cancel check under canonical child exclusion. Failed, abandoned or escalated children return explicit bounded status/evidence references, never a fabricated successful artifact. A workflow waiting at a human gate is reported as waiting, not collected as success.

Drive polls eligible ordinary roots in stable slot order within finite positive `max_wall_s` and `max_concurrent`; contention/failure is reported per child. A timeout preserves identities and reports partial progress. No unbounded executor queue or loop is admitted. Verify the concurrency cap at actual process boundaries, not only helper call counts. Reports stay compact, omit full conversations, and point to durable evidence.

P4 consumes these verified source receipts and introduces its own explicit required source set; no caller can use P3 collection as stage or landing authority. P5 must reconcile current-generation child records before enabling trusted or decision-driven replacements for children.

Implementation seam authorized by coordinator: `foreman/decisions.py` must select the current child slot and scope its requests/attention to that child. Preserve owner-work and P2 decision behavior. This is necessary independent-run routing, not new orchestration. Prove with ordinary child execution plus P2 regressions.
