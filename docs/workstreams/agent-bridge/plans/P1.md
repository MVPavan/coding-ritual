# Sequential bridge implementation plan

**Origin:** approved workflow coordination spec and roadmap P1; prior phase-execution-interpreter-bridge plan v12.
**Goal:** normal named-stage execution reaches verified landing and durable stage closure, then a second stage starts from that result.
**Out of scope:** LLM decision execution, concurrent child admission, concurrent landing, development branch merge/push.
**Constraints:** preserve existing uncommitted authority work; canonical root pins remain authoritative; use authenticated gate closure rather than redundant weaker signature checks; graph-approved artifact and exact verification policy bind every durable landing transition. No empty verification success. Fable review occurs after the substantial bridge milestone, per owner direction.

## File map

- bridge/authority.py: derive landing authority from the actual authenticated immutable ship gate.
- bridge/models.py and admission.py: persist admitted verification policy identity with stage/root relation and preserve it on recovery.
- bridge/landing.py and a focused verification module if needed: observe checks and bind complete results to candidate, policy, intent and receipt.
- bridge/command.py, adapter.py and retry.py: invoke authoritative landing/recovery and close only verified completed work; resolve existing correspondence/retry defects.
- foreman/config.py and __main__.py: explicit local verification configuration and correct command arguments.
- tests/test_bridge_authority.py, test_phase_bridge.py, test_phase_bridge_cli.py and narrowly added verification tests: regression and end-to-end command seams.
- .claude/skills/execution/SKILL.md and operating docs: use the actual command, no duplicate stage loop.
